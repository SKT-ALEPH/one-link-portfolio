비밀번호 없이
나만의 공간 열기

과제 8 · 패스키 인증 구현 설명서

기존 소개는 누구나 볼 수 있습니다. 비공개 메모와 기관 이름은 모두 과제용 가상 내용이며, 실제 연락처·신분증 번호·비밀값을 제출하지 않습니다.

결과물: 공개 소개 페이지
소스: GitHub 저장소

① 무엇으로 붙였나

라이브러리 방식입니다. 기존 React + Vite 페이지에 Node.js + Express 서버를 추가하고, SimpleWebAuthn 14로 패스키 등록 응답과 로그인 서명을 검증합니다. SQLite는 공개키·계정·일회용 질문·세션의 해시·가상 메모를 저장합니다. Caddy가 HTTPS를 제공하고 Docker Compose로 실행합니다.

로그인 뒤에는 임의의 세션값을 HttpOnly·Secure·SameSite=Strict 쿠키로 전달합니다. 서버에는 원문 대신 SHA-256 해시만 저장합니다. 세션은 1시간 후 만료되고 로그아웃하면 즉시 서버에서 삭제됩니다.

② 왜 그걸 골랐나

보유한 Vultr 서버에서 시작해 나중에 NAS로 옮기기 위해 서비스 업체 전용 인증 기능 대신 직접 옮길 수 있는 구성을 선택했습니다. 암호 검증 알고리즘은 직접 구현하지 않고 전용 라이브러리에 맡겼습니다. 계정 두 개와 소량의 메모에는 별도의 데이터베이스 서버 없이 SQLite로 충분합니다.

이전할 때는 portfolio-passkey.duckdns.org 도메인과 RP ID, 계정·공개키 데이터베이스를 유지합니다. DB는 앱을 잠시 정지한 상태에서 옮기고, 기존 세션은 종료한 후 패스키로 재로그인합니다.

최초 등록은 관리자만 발급할 수 있는 24시간 일회용 링크 사용

등록·로그인 질문은 2분 동안 유효하며, 검증 시 원자적으로 삭제해 재사용을 막습니다. 질문은 시작한 브라우저에도 연결됩니다. 추가 등록과 삭제에는 최근 10분 이내의 본인 확인이 필요합니다. 비공개 조회는 주소나 본문의 계정값이 아니라 서버 세션을 기준으로 처리합니다.

공개키는 로그인 후 ‘내 패스키 → 서버에 저장된 공개키 보기’에서 확인할 수 있습니다. 등록 요청에는 clientDataJSON과 attestationObject 등이 포함되며 개인키는 없습니다. 저장된 공개키는 COSE 형식을 base64url로 표시합니다.

④ 안 열리는 것을 확인한 기록

요청·응답 전체 기록 보기(JSON) · 쿠키와 초대값은 가렸고, 비공개 메모 본문도 제외했습니다.

검사통과 요청거절 요청
로그인 없이 열기정상 로그인 뒤 자료 조회 200세션 없이 자료 조회 401
남의 패스키로 열기A·B 각각 자기 자료 200A→B, B→A 요청 모두 403
질문 재사용새 질문 + 올바른 서명 200같은 질문 재전송 400, 틀린 서명 403
패스키 삭제 뒤 로그인A의 남은 패스키로 200삭제한 패스키로 403
로그아웃로그아웃 요청 204이전 세션값 재사용 401

계정별 가상 자료는 각 3개이며, 상호 접근 거절 전후에도 각 3개로 유지됐습니다. 쿼리와 본문에 다른 계정을 넣어도 자기 자료만 돌아오는 것을 확인했습니다. 등록 취소 후 저장 건수 0, 다른 출처·만료 질문·동시 재사용·마지막 키 삭제 거절도 검사했습니다.

검증 범위: JSON 기록은 로컬 소프트웨어 WebAuthn 인증기가 만든 실제 P-256 서명을 서버 라이브러리로 검증한 결과입니다. 테스트 개인키는 검사 프로세스의 메모리에만 존재하며 서버나 제출 기록에 저장하지 않습니다. Google 비밀번호 관리자나 사용자 실제 기기를 검사한 기록으로 주장하지 않습니다.

배포 주소 검증: 공개 HTTPS 서버에서도 Chromium 가상 CTAP2 인증기로 두 계정의 등록, 한 계정의 두 패스키, 상호 접근 차단, 로그아웃 세션 재사용 거절, 질문 재사용 거절, 삭제 후 로그인까지 12개 검사를 통과했습니다. 실제 HTTPS 요청·응답 기록

두 패스키 목록 화면 · 남은 키로 로그인한 화면 · 삭제한 키 거절 화면 · 로그인 전 모바일 화면

실제 기기 확인 대기: 소유자가 서로 다른 두 패스키를 등록하고, 저장 위치를 확인한 뒤 하나를 삭제하여 남은 키로 로그인하는 최종 실기 기록은 별도로 남겨야 합니다. 위 가상 인증기는 사용자 실제 기기의 패스키 저장 위치를 증명하지 않습니다. 배포 검증에 사용한 임시 계정은 검사 후 제거합니다.

⑤ AI와 나

AI에게 맡긴 일: 인증 서버·화면 구현, Vultr 배포, 접근 차단 검사와 설명서 작성.

내가 직접 판단한 일: 프레임워크 변경 전 설계 확인을 요청하고, 보유한 Vultr를 먼저 사용한 뒤 NAS로 옮기는 운영 방향을 선택했습니다.

AI 제안을 따르지 않은 일: AI가 먼저 제안한 Sites 이전 대신 Vultr와 DuckDNS를 선택했습니다.

⑥ 아직 못 막은 것

  • 로그인한 기기 자체가 탈취되거나 악성 프로그램에 감염된 경우, 공격자가 열린 화면이나 유효한 세션을 이용하는 것까지 막지는 못합니다.
  • 사용 가능한 패스키를 전부 잃었을 때 자동 복구 기능은 없습니다. 마지막 등록 키 삭제는 차단하지만, 기기 분실까지 방지하지는 못합니다.
  • 요청 횟수 제한은 단일 서버 메모리 기준입니다. 대규모 분산 공격에 대한 전문 방어 서비스와 장기 무중단 운영은 구성하지 않았습니다.
  • 암호화된 외부 백업과 정기 복구 훈련은 운영자가 별도로 준비해야 합니다. 서버 한 대의 디스크 장애까지 이 구성만으로 해결하지는 못합니다.

짧은 확인 방법 · 4줄

어디로 가나요: 위 결과물 주소의 공개 소개로 갑니다.
세 단계 안에 무엇을 하나요: 소개 확인 → ‘나만의 공간’ 클릭 → 잠김 화면 확인.
무엇이 보이면 통과인가요: 공개 소개는 바로 열리고, 로그인 전에는 메모 본문이 보이지 않습니다.
안 될 때는 무엇이 보이나요: 취소·실패 안내가 나오며 비공개 자료 요청은 401 또는 403으로 거절됩니다.

심사자는 패스키를 등록하거나 비공개 공간을 열 필요가 없습니다.
